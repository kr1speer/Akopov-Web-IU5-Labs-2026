## 3. Задание

### 3.1. Основное задание

Разработать REST API сервис на платформе `Node.js` для управления инженерными задачами и информацией о самолетах Boeing.

Данные должны храниться в формате JSON.

Необходимо реализовать следующие HTTP-методы:

- `GET /stocks` — получение списка записей;
- `GET /stocks/:id` — получение записи по ID;
- `POST /stocks` — создание новой записи;
- `PATCH /stocks/:id` — частичное обновление объекта;
- `DELETE /stocks/:id` — удаление записи.

Дополнительно реализуется фильтрация данных по названию (`title`).

---

### 3.2. Дополнительное задание (Реализация PUT)

Изучить различия между HTTP-методами `PUT` и `PATCH`.

Реализовать поддержку метода `PUT`, предназначенного для полной замены объекта.  
При выполнении запроса должна выполняться проверка обязательных полей.

## 4. Теория и реализация (Примеры из кода)

### 4.1. Слоистая архитектура и Middleware

**Теория:**  
Для повышения читаемости и удобства поддержки проекта приложение разделено на несколько слоев:
- роуты;
- контроллеры;
- сервисы;
- работа с файловой системой.

Такой подход позволяет разделить ответственность между частями приложения и избежать смешивания бизнес-логики с обработкой HTTP-запросов.

Дополнительно используются middleware-функции Express.js для обработки JSON и логирования запросов.

**Пример из кода:**

```javascript
// Встроенный middleware для обработки JSON
app.use(express.json());

// Middleware для логирования запросов
app.use((req, res, next) => {
    console.log(`[${new Date().toISOString()}] ${req.method} ${req.url}`);
    next();
});
```
### 4.2. Разница между PUT и PATCH

**Теория:**

#### PATCH — частичное обновление

Метод `PATCH` используется для изменения отдельных полей объекта.  
При обновлении остальные данные сохраняются без изменений.

В проекте частичное обновление реализовано через оператор расширения (`...`), который объединяет старые и новые данные.

#### PUT — полная замена

Метод `PUT` полностью заменяет существующий объект новым.  
Если какое-либо поле отсутствует в запросе, оно должно быть удалено либо заменено значением по умолчанию.

Такой подход обеспечивает строгую синхронизацию данных между клиентом и сервером.

---

### 4.3. Маршрутизация и контроллеры

**Теория:**  
Контроллеры отвечают за обработку запросов пользователя и формирование HTTP-ответов.

Перед созданием новой записи выполняется проверка обязательных полей, что предотвращает сохранение некорректных данных.

**Пример из кода:**

```javascript
const createStock = (req, res) => {
    const stockData = req.body;

    // Проверка обязательных полей
    if (!stockData.src || !stockData.title || !stockData.text) {
        return res.status(400).json({
            error: 'Не все поля заполнены'
        });
    }

    const newStock = stocksService.create(stockData);

    res.status(201).json(newStock);
};
```
Такой подход позволяет централизованно контролировать корректность входящих данных.

---

### 4.4. Бизнес-логика и хранение данных (Сервисы)

**Теория:**  
Вся работа с данными вынесена в отдельный сервисный слой (`stocksService.js`).

Сервисы инкапсулируют:
- чтение JSON-файлов;
- запись данных;
- поиск объектов;
- генерацию идентификаторов.

При создании новой записи автоматически вычисляется следующий свободный ID.

**Пример из кода:**

```javascript
const create = (stockData) => {
    const stocks = fileService.readData(dataFilePath);

    const newId = stocks.length > 0
        ? Math.max(...stocks.map(s => s.id)) + 1
        : 1;

    const newStock = {
        id: newId,
        ...stockData
    };

    stocks.push(newStock);

    fileService.writeData(dataFilePath, stocks);

    return newStock;
};
```
Благодаря сервисному слою логика работы с данными остается независимой от HTTP-маршрутов.
